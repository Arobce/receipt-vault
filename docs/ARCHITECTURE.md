## Architecture Overview

ReceiptVault is deployed as a cloud-native application on AWS using a containerized microservices architecture. The system consists of three compute workloads, a managed relational database, object storage, and an event-driven serverless processor.

**Compute Layer:**
- **Web Frontend** - Next.js 16 (standalone mode) running on ECS Fargate
- **API Backend** - Express 5 running on ECS Fargate
- **Receipt Processor** - Node.js Lambda function triggered by S3 events

**Data Layer:**
- **PostgreSQL 16** on Amazon RDS (db.t3.micro)
- **Amazon S3** for receipt image storage

**Networking Layer:**
- **Application Load Balancer (ALB)** with path-based routing
- **ECS Fargate** for zero-server container orchestration

**CI/CD Layer:**
- **CodePipeline** orchestrating three **CodeBuild** projects
- **GitHub** source via CodeStar Connection

## Infrastructure Components

### Amazon ECS (Fargate)

The application runs on a single ECS cluster (`receiptvault`) with two services:

| Service | Container | Port | CPU | Memory | Image Source |
|---------|-----------|------|-----|--------|--------------|
| `receiptvault-api-service` | receiptvault-api | 4000 | 256 | 512 MB | ECR `receiptvault-api` |
| `receiptvault-web-service` | receiptvault-web | 3000 | 256 | 512 MB | ECR `receiptvault-web` |

Both services run on Fargate (serverless), meaning there are no EC2 instances to manage. Tasks are launched in the default VPC with public subnets and auto-assigned public IPs.

### Amazon RDS

- **Engine:** PostgreSQL 16
- **Instance:** db.t3.micro (Free Tier eligible)
- **Storage:** 20 GB gp2
- **Endpoint:** `receiptvault-db.cozcm228shsc.us-east-1.rds.amazonaws.com:5432`
- **Connection:** SSL with `sslmode=no-verify` (RDS uses self-signed certificates)
- **Access:** Security group allows inbound on port 5432

### Amazon S3

- **Bucket:** `receiptvault-receipts-111584419354`
- **Purpose:** Receipt image storage
- **Structure:** `uploads/{userId}/{uuid}.{extension}`
- **Event Notification:** `ObjectCreated` on prefix `uploads/` triggers Lambda
- **Access:** Presigned URLs generated by the API (1-hour expiry)

### AWS Lambda

- **Function:** `receiptvault-processor`
- **Runtime:** Node.js 20
- **Memory:** 512 MB
- **Timeout:** 60 seconds
- **Trigger:** S3 event notification (ObjectCreated on `uploads/` prefix)
- **Environment Variables:** `DATABASE_URL`, `AWS_REGION`

### Application Load Balancer

- **Name:** `receiptvault-alb`
- **DNS:** `receiptvault-alb-1281619146.us-east-1.elb.amazonaws.com`
- **Routing Rules:**
  - `/api/*` -> API target group (port 4000)
  - `/*` (default) -> Web target group (port 3000)

### Amazon ECR

Two private repositories store Docker images:
- `receiptvault-api` - Express API images
- `receiptvault-web` - Next.js frontend images

Images are tagged with both `latest` and the short commit hash (e.g., `abc1234`).

## Data Flow: User Registration & Authentication

```
User (Browser)
  |
  | POST /api/auth/register {email, password, name}
  v
ALB (receiptvault-alb)
  |
  | Path: /api/* -> API Target Group
  v
ECS Fargate (receiptvault-api)
  |
  | 1. Zod validates input (email format, password >= 8 chars)
  | 2. bcrypt hashes password (12 salt rounds)
  | 3. Prisma creates User record
  v
RDS PostgreSQL
  |
  | Returns: User record (id, email, name)
  v
ECS Fargate (receiptvault-api)
  |
  | 4. Signs JWT access token (15 min expiry)
  | 5. Signs JWT refresh token (7 day expiry)
  | 6. Returns {user, accessToken, refreshToken}
  v
ALB -> User (Browser)
  |
  | 7. Frontend stores tokens in localStorage
  | 8. Redirects to /dashboard
  v
Authenticated Session Active
```

**Token Refresh Flow:**
When the access token expires and the API returns 401, the frontend automatically calls `POST /api/auth/refresh` with the refresh token to obtain a new access token. If the refresh token is also expired, the user is redirected to the login page.

**Security Details:**
- Passwords are never stored in plain text; bcrypt with 12 salt rounds is used
- JWT secrets are stored in AWS Systems Manager Parameter Store as SecureString
- Auth routes are rate-limited: 20 requests per 15 minutes per IP address

## Data Flow: Receipt Upload & Processing

This is the core data flow of the application, spanning three compute services.

### Phase 1: Upload (User -> API -> S3)

```
User (Browser)
  |
  | POST /api/receipts/upload (multipart/form-data)
  | File: receipt image (JPG, PNG, HEIC, or PDF, max 10 MB)
  v
ALB -> ECS Fargate (receiptvault-api)
  |
  | 1. Auth middleware validates JWT Bearer token
  | 2. Multer middleware validates file type and size
  | 3. Generates S3 key: uploads/{userId}/{uuid}.{ext}
  | 4. Uploads file to S3 bucket
  v
Amazon S3 (receiptvault-receipts-111584419354)
  |
  | File stored at: uploads/{userId}/{uuid}.{ext}
  v
ECS Fargate (receiptvault-api)
  |
  | 5. Creates Receipt record in database:
  |    - s3Key = "uploads/{userId}/{uuid}.{ext}"
  |    - status = PENDING
  |    - originalName = original filename
  v
RDS PostgreSQL
  |
  | Receipt record created
  v
API returns {id, s3Key, originalName, status: "PENDING", createdAt}
```

### Phase 2: Processing (S3 Event -> Lambda -> Textract -> Database)

```
Amazon S3
  |
  | S3 Event Notification: ObjectCreated on prefix "uploads/"
  v
AWS Lambda (receiptvault-processor)
  |
  | 1. Receives S3 event with bucket name and object key
  | 2. Queries PostgreSQL for Receipt record matching s3Key
  | 3. Updates receipt status -> PROCESSING
  v
RDS PostgreSQL (status = PROCESSING)
  |
  v
AWS Lambda
  |
  | 4. Calls AWS Textract AnalyzeExpense API
  |    - Passes S3 bucket + key reference (Textract reads directly from S3)
  |    - Textract performs OCR + expense field extraction
  v
AWS Textract
  |
  | Returns structured expense data:
  |   - VENDOR_NAME (merchant)
  |   - TOTAL (amount)
  |   - INVOICE_RECEIPT_DATE (date)
  |   - LINE_ITEMS [{description, amount}, ...]
  v
AWS Lambda
  |
  | 5. Parses Textract response:
  |    - Extracts merchant name from VENDOR_NAME field
  |    - Parses total amount from TOTAL field (strips currency symbols)
  |    - Parses date from INVOICE_RECEIPT_DATE field
  |    - Extracts line items (ITEM + PRICE pairs)
  |
  | 6. Categorizes merchant using keyword matching:
  |    - e.g., "Walmart" -> Groceries, "Shell" -> Gas & Auto
  |    - Falls back to "Other" if no keyword match
  |    - Looks up Category record in database
  |
  | 7. Updates Receipt record:
  |    - merchant, totalAmount, receiptDate, categoryId
  |    - rawTextract (full Textract JSON response)
  |    - lineItems (parsed array)
  |    - status -> PROCESSED
  v
RDS PostgreSQL (status = PROCESSED)
```

### Phase 3: Viewing (User -> API -> S3 Presigned URL)

```
User (Browser)
  |
  | GET /api/receipts/{id}
  v
ALB -> ECS Fargate (receiptvault-api)
  |
  | 1. Auth middleware validates JWT
  | 2. Fetches receipt from database (ensures userId matches)
  | 3. Generates presigned S3 URL for the receipt image (1-hour expiry)
  | 4. Returns receipt data + imageUrl
  v
User (Browser)
  |
  | Renders receipt detail page
  | <img> tag loads image directly from S3 via presigned URL
  v
Amazon S3 (direct download via presigned URL)
```

**Error Handling:**
If Textract fails or any error occurs during Lambda processing, the receipt status is set to `FAILED`. The user sees this status in the UI and can re-upload if needed.

## Data Flow: Dashboard & Analytics

```
User (Browser)
  |
  | GET /api/dashboard/summary?period=month&date=2026-04
  v
ALB -> ECS Fargate (receiptvault-api)
  |
  | 1. Auth middleware validates JWT
  | 2. Calculates date range from period + date params
  | 3. Executes aggregation queries against PostgreSQL:
  |    a. SUM(totalAmount) for total spent
  |    b. COUNT(*) for receipt count
  |    c. GROUP BY categoryId for category breakdown
  |    d. GROUP BY DATE(receiptDate) for daily totals
  |    (All queries filter: userId match, status = PROCESSED, within date range)
  v
RDS PostgreSQL
  |
  | Returns aggregated results
  v
ECS Fargate (receiptvault-api)
  |
  | 4. Formats response with category names and icons
  | 5. Returns {totalSpent, receiptCount, categoryBreakdown, dailyTotals}
  v
User (Browser)
  |
  | Renders dashboard:
  |   - Summary cards (total spent, count, average)
  |   - Daily spending bar chart
  |   - Category breakdown with percentages
```

## Data Flow: CSV Export

```
User (Browser)
  |
  | GET /api/export/csv?startDate=2026-01-01&endDate=2026-04-01&category=Groceries
  v
ALB -> ECS Fargate (receiptvault-api)
  |
  | 1. Auth middleware validates JWT
  | 2. Queries receipts with filters (date range, category)
  |    - Only includes status = PROCESSED
  |    - Only includes user's own receipts
  | 3. Formats as CSV with headers: date, merchant, category, amount, currency
  | 4. Returns CSV file as download
  v
User (Browser) downloads .csv file
```

## CI/CD Pipeline

### Pipeline Architecture

```
GitHub Repository (main branch)
  |
  | Push event detected by CodeStar Connection
  v
AWS CodePipeline (receiptvault-pipeline)
  |
  | Source Stage: Pulls latest code from GitHub
  v
  +---> CodeBuild: receiptvault-api-build (parallel)
  |       |
  |       | 1. Login to ECR
  |       | 2. cd apps/api
  |       | 3. docker build --platform linux/amd64
  |       | 4. Push to ECR (tagged: latest + commit hash)
  |       | 5. aws ecs update-service --force-new-deployment
  |       v
  |     API containers roll out on ECS (rolling update)
  |
  +---> CodeBuild: receiptvault-web-build (parallel)
  |       |
  |       | 1. Login to ECR
  |       | 2. cd apps/web
  |       | 3. docker build --platform linux/amd64
  |       |    --build-arg NEXT_PUBLIC_API_URL={ALB_URL}/api
  |       | 4. Push to ECR (tagged: latest + commit hash)
  |       | 5. aws ecs update-service --force-new-deployment
  |       v
  |     Web containers roll out on ECS (rolling update)
  |
  +---> CodeBuild: receiptvault-lambda-build (parallel)
          |
          | 1. cd apps/lambda && npm ci
          | 2. prisma generate && tsc
          | 3. Bundle dist/ + pruned node_modules into function.zip
          | 4. aws lambda update-function-code --zip-file
          v
        Lambda function code updated
```

### Build Details

**API Build:**
- Multi-stage Dockerfile: build stage (compile TypeScript, generate Prisma) + runtime stage (copy dist + node_modules)
- Dummy `DATABASE_URL` used during build for Prisma generate (no actual DB connection needed)
- Platform: `linux/amd64` (required for Fargate)

**Web Build:**
- Multi-stage Dockerfile: build stage (next build in standalone mode) + runtime stage (copy .next/standalone + static + public)
- `NEXT_PUBLIC_API_URL` is baked into the image at build time via `--build-arg` (Next.js inlines public env vars during build)
- Platform: `linux/amd64`

**Lambda Build:**
- TypeScript compiled to `dist/`
- Production `node_modules` copied into package
- Prisma engine binaries stripped (non-PostgreSQL WASM compilers removed) to keep zip under Lambda's 250 MB limit
- Deployed via `aws lambda update-function-code`

## Networking & Routing

### Request Flow

```
Internet
  |
  v
Application Load Balancer (HTTP:80)
  |
  |--- Path: /api/*  --->  API Target Group  --->  ECS Task (port 4000)
  |
  |--- Path: /*      --->  Web Target Group  --->  ECS Task (port 3000)
```

The ALB provides:
- **Stable DNS endpoint** - no hardcoded IPs needed; ECS tasks can be replaced without URL changes
- **Path-based routing** - single entry point for both frontend and API
- **Health checks** - monitors container health, replaces unhealthy tasks
- **Load distribution** - distributes traffic across multiple tasks (if scaled)

### Internal Connections

```
ECS (API) -----> RDS PostgreSQL (port 5432, SSL with sslmode=no-verify)
ECS (API) -----> S3 (AWS SDK, IAM task role)
Lambda    -----> RDS PostgreSQL (port 5432, SSL with sslmode=no-verify)
Lambda    -----> S3 (read receipt images for Textract)
Lambda    -----> Textract (AnalyzeExpense API)
S3        -----> Lambda (event notification trigger)
```

### Security Groups

| Resource | Inbound Rules |
|----------|--------------|
| ALB | 0.0.0.0/0 on port 80 (HTTP) |
| ECS Tasks | ALB security group on ports 3000, 4000 |
| RDS | ECS security group + Lambda on port 5432 |

## Security Architecture

### Secrets Management

All sensitive configuration is stored in **AWS Systems Manager Parameter Store** as SecureString (encrypted with AWS KMS):

| Parameter | Used By |
|-----------|---------|
| `/receiptvault/database-url` | API (ECS), Lambda |
| `/receiptvault/jwt-secret` | API (ECS) |
| `/receiptvault/jwt-refresh-secret` | API (ECS) |

ECS tasks retrieve these at launch via the task execution role. The execution role has `ssm:GetParameters` and `kms:Decrypt` permissions.

### IAM Roles

| Role | Purpose | Key Permissions |
|------|---------|----------------|
| `ecsTaskExecutionRole` | ECS task startup | ECR pull, SSM read, KMS decrypt, CloudWatch logs |
| `receiptvault-task-role` | API runtime | S3 read/write (receipts bucket) |
| `receiptvault-lambda-role` | Lambda runtime | S3 read, Textract, RDS connect, CloudWatch logs |
| `receiptvault-codebuild-role` | CI/CD builds | ECR push, ECS update, Lambda update, S3, CloudWatch logs |

### Application Security

- **Authentication:** JWT Bearer tokens with short-lived access (15 min) + long-lived refresh (7 days)
- **Password Hashing:** bcrypt with 12 salt rounds
- **Input Validation:** Zod schemas on all API endpoints
- **Rate Limiting:** 20 req/15 min on auth routes
- **CORS:** Restricted to ALB origin
- **Soft Deletes:** Receipts are never permanently deleted; `deletedAt` timestamp is set
- **Ownership Enforcement:** All receipt queries filter by authenticated `userId`

## Monitoring & Observability

### CloudWatch Log Groups

| Log Group | Source | Retention |
|-----------|--------|-----------|
| `/ecs/receiptvault-api` | API container stdout/stderr | 14 days |
| `/ecs/receiptvault-web` | Web container stdout/stderr | 14 days |
| `/aws/lambda/receiptvault-processor` | Lambda function logs | 14 days |

### CloudWatch Alarms

| Alarm | Metric | Threshold |
|-------|--------|-----------|
| API High Error Rate | Metric filter on "error" in API logs | > 10 errors in 5 min |
| Lambda Failures | Lambda Errors metric | > 3 errors in 5 min |
| RDS High CPU | CPUUtilization | > 80% for 5 min |
| ALB 5xx Errors | HTTPCode_ELB_5XX_Count | > 10 in 5 min |

### CloudWatch Dashboard

The `ReceiptVault-Monitoring` dashboard provides a single pane of glass for:
- ECS service CPU and memory utilization
- API request counts and error rates
- Lambda invocations and error counts
- RDS CPU utilization and database connections
- ALB request count and response times
